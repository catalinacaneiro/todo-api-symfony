# Symfony Todo API

A small JSON API for creating, listing, updating, and deleting tasks stored in
MySQL. It uses Symfony 8.1, Doctrine ORM 3.7, Doctrine Migrations, Symfony
Serializer and Validator, and PHPUnit 13.3 with Symfony BrowserKit for tests.
Routes use PHP attributes; POST and PATCH bind JSON to input DTOs through
`#[MapRequestPayload]`. Doctrine maps the `Task` entity to the database.

## Requirements

- `composer.json` requires PHP **>=8.4** and the `ctype` and `iconv` extensions.
  Installed dependencies may impose a higher PHP requirement; Composer checks
  these during installation.
- Composer is required to install dependencies. `composer.json` does **not**
  specify a minimum Composer version; it requires Symfony Flex `^2`.
- A running MySQL server and PHP's PDO MySQL driver (`pdo_mysql`).
- Symfony CLI for the local server commands below.

## Local setup

From the project directory, install dependencies, including development tools:

```sh
composer install
```

Create `.env.local` and configure `DATABASE_URL` with your local settings:

```dotenv
DATABASE_URL="mysql://todo_user:CHANGE_ME@127.0.0.1:3306/todo_symfony?serverVersion=8.0.32&charset=utf8mb4"
```

These are placeholder credentials. Replace the username, password, and server
version with your own values. URL-encode special characters in credentials.
MAMP users should use their configured MySQL port instead of the example `3306`;
the local setup used for this project uses `8889`.
Keep real credentials in the git-ignored `.env.local`, not the committed `.env`.
The MySQL user needs permission to create the database and apply migrations.

Create the database and apply the existing migration:

```sh
symfony console doctrine:database:create
symfony console doctrine:migrations:migrate --no-interaction
```

Without Symfony CLI, use `php bin/console` in place of `symfony console`.
The checked-in migration creates the `task` table; it does not create a
`messenger_messages` table.

Start the local server over HTTP:

```sh
symfony serve -d --no-tls --port=8000
```

The examples below use `http://127.0.0.1:8000`.

## Task response

GET returns an array of tasks; successful POST and PATCH return one task object.
Each task has exactly these five fields:

| Field | Type | Initial value |
| --- | --- | --- |
| `id` | integer | Generated by the database when saved. |
| `title` | string | Supplied by the caller; required, with no valid default. |
| `description` | string or null | `null` when omitted on creation. |
| `completed` | boolean | `false` on creation. |
| `createdAt` | string | Set by the backend at creation, formatted as an ISO 8601 timestamp with timezone offset. |

For example (the ID and timestamp will vary):

```json
{
  "id": 1,
  "title": "Learn Symfony",
  "description": "Build a Todo API",
  "completed": false,
  "createdAt": "2026-10-05T12:00:00+00:00"
}
```

## Endpoints and curl examples

Use `-i` to display the HTTP status and headers. For PATCH and DELETE, replace
`1` with the ID returned by POST.

### GET /tasks

```sh
curl -i http://127.0.0.1:8000/tasks
```

Returns **200 OK** with a JSON array, ordered by `createdAt` descending, then
`id` descending (newest first). An empty database returns `[]`.

### POST /tasks

```sh
curl -i -X POST http://127.0.0.1:8000/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"Learn Symfony","description":"Build a Todo API"}'
```

Returns **201 Created** with the saved task. Only `title` and `description`
are creation inputs. Supplied `id`, `completed`, or `createdAt` values are
ignored; the backend owns their initial values.

### PATCH /tasks/{id}

```sh
curl -i -X PATCH http://127.0.0.1:8000/tasks/1 \
  -H 'Content-Type: application/json' \
  -d '{"title":"Learned Symfony","completed":true}'
```

Returns **200 OK** with the updated task. Updates are partial: omitted fields
keep their existing values. `id` and `createdAt` cannot be updated.

Clear the description by explicitly sending `null`:

```sh
curl -i -X PATCH http://127.0.0.1:8000/tasks/1 \
  -H 'Content-Type: application/json' \
  -d '{"description":null}'
```

Returns **200 OK**, with `description` set to `null` and other fields preserved.

### DELETE /tasks/{id}

```sh
curl -i -X DELETE http://127.0.0.1:8000/tasks/1
```

Returns **204 No Content** with an empty body. Repeating the deletion returns
**404 Not Found**. PATCH with a valid payload for a missing task also returns
**404**, with `{"error":"Task not found."}`.

## Validation

- Titles must be strings, must not be empty or whitespace-only, and must be at
  most 255 characters. Whitespace is checked for validation, not trimmed from
  the stored title. Missing POST titles default internally to an empty string
  and return **422 Unprocessable Entity**.
- Descriptions may be strings or `null`.
- PATCH accepts only `title`, `description`, and `completed`. `completed` must
  be a JSON boolean (`true` or `false`).
- PATCH requires a non-empty JSON object. Empty objects, non-object payloads,
  unknown fields (including `id` and `createdAt`), invalid types, and malformed
  JSON return **400 Bad Request**.
- Invalid titles return **422 Unprocessable Entity**. The existing POST tests
  also expect **422** for null/array titles and array descriptions.
- Invalid requests are not saved. PATCH validates the proposed changes before
  modifying the stored entity.

For example, an invalid title returns **422**:

```sh
curl -i -X POST http://127.0.0.1:8000/tasks \
  -H 'Content-Type: application/json' \
  -d '{"title":"   "}'
```

An empty update returns **400**:

```sh
curl -i -X PATCH http://127.0.0.1:8000/tasks/1 \
  -H 'Content-Type: application/json' \
  -d '{}'
```

## Tests and verification

Run the existing suite from the project directory:

```sh
php bin/phpunit
```

The `bin/phpunit` entry point loads the installed PHPUnit runner; alternatively,
use `vendor/bin/phpunit`.

The automated controller tests extend `WebTestCase` and make HTTP requests
through Symfony's test client. They mock Doctrine's entity manager and
repositories, so they check responses, validation, and persistence calls
without verifying a real database connection or migration.

Earlier manual curl tests, recorded in `NOTES.md`, verified CRUD against the
local MySQL database: create and retrieve a task, persist partial updates and
clear descriptions, reject invalid updates, delete a task, and return 404 on
repeated deletion. These manual checks are separate from the mocked automated
tests.
